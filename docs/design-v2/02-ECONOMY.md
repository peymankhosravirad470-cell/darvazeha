# سند ۰۲ — اقتصاد بازی: توکن، کیف پول، دفترکل و ماتریس پاداش

> **نسخهٔ v2.0 پیش‌نویس برای تصویب | ۲۰۲۶-۱۱-۰۲ | وابسته به: سند ۰۱ §۵، سند ۱۴ (داده)، سند ۱۱ (ضدتقلب)، سند ۱۵ (شبیه‌سازی)**
> قانون ۷ دستور کارفرما: **هیچ عدد اقتصادی در این سند قطعی نیست.** همهٔ اعداد با برچسب [عدد آزمایشی] فقط برای شبیه‌سازی اولیهٔ سند ۱۵ به‌کار می‌روند.

---

## ۱. هدف

تعریف ارز واحد بازی، منابع ورود و خروج آن، قاعدهٔ جلوگیری از پاداش دوبله بین پنج مسیر فعالیت، و چارچوب کنترل تورم — به‌گونه‌ای که هیچ فعالیتی نتواند دو بار توکن تولید کند و هیچ سیستم نتواند دارایی شخصی را بدون رضایت آگاهانه در معرض ریسک بگذارد.

## ۲. توکن و کیف پول

| مورد | طراحی |
|---|---|
| نام پیشنهادی | **«سکهٔ سرزمین»** [نیازمند تصویب کارفرما — گزینه‌های دیگر: «شَرَف»، «میثره»، بدون نام و فقط «توکن»] |
| واحد جزئی | ندارد (عدد صحیح)؛ نمایش با اعداد فارسی |
| مالکیت | فقط بازیکن؛ سکونتگاه خزانهٔ مستقل دارد (سند ۰۹) — توکن شخصی هرگز خودکار به خزانه منتقل نمی‌شود |
| انتقال مستقیم بین بازیکنان | **پیش‌فرض: ممنوع** [پیشنهادی]. تنها راه جابه‌جایی ارزش بین دو بازیکن، معاملهٔ واقعی در بازار (کالا↔توکن) یا سهم مصوب پروژه است. این قاعده بزرگ‌ترین سدّ جلوی شست‌وشو و معاملهٔ صوری است [نیازمند تصویب کارفرما] |
| تبدیل ستاره به توکن | ممنوع [پیشنهادی] — ستاره شاخص پیشرفت فردی است، نه دارایی (سند ۱۷-C5) |
| نگهداری | کیف پول واحد سراسری در سرور (سند ۱۴ §۳)؛ آفلاین v1 توکن ندارد |

## ۳. دفترکل (Ledger)

- **تغییرناپذیر/قابل ممیزی [قطعی]:** رکوردهای دفترکل هرگز ویرایش یا حذف نمی‌شوند؛ اصلاح فقط با رکورد معکوس (reversal) و مرجع به رکورد اصلی.
- هر `LedgerEntry`: شناسه، زمان، حساب (بازیکن/خزانه/سیستم)، جهت (+/−)، مقدار، دستهٔ ترک (`INDIVIDUAL | COLLECTIVE | SYSTEM_SOURCE | SYSTEM_SINK`)، `event_id` مرجع، طرف مقابل، توضیح.
- **موجودی = جمع دفترکل**؛ هیچ موجودی «خارج از دفترکل» وجود ندارد. بازسازی تاریخچهٔ مالی هر بازیکن از دفترکل ممکن است [قطعی].
- ترک‌ها جداگانه جمع می‌شوند (حسابداری دو مسیر) اما در یک کیف پول یکی می‌شوند [قطعی — «جدا از نظر حسابداری، مرتبط از نظر پیشرفت»].

## ۴. ماتریس سیاست پاداش (Reward Policy Matrix) — قلب جلوگیری از پاداش دوبله

### ۴.۱ اصل [پیشنهادی]

هر **رویداد فعالیت** (Activity Event) با شناسهٔ یکتای `evt_*` در سیستم ثبت می‌شود. هر رویداد می‌تواند حداکثر **یک پاداش توکنی اصلی** (`token_primary`) بگیرد؛ سایر شناسایی‌ها (ستاره، نشان، امتیاز هماورد، امتیاز سکونتگاه) غیرتوکنی‌اند و طبق ماتریس زیر آزادند.

### ۴.۲ کلاس‌های شناسایی (grant_class)

`token_primary` (توکن) · `star` (ستارهٔ پیشرفت) · `badge` (نشان) · `item` (آیتم/محصول) · `score_war` (امتیاز هماورد) · `score_settlement` (امتیاز مشارکت سکونتگاه) · `score_progress` (امتیاز پیشرفت) · `reputation` (اعتبار)

### ۴.۳ ماتریس مجاز (✓ مجاز، ✗ ممنوع، △ فقط طبق قاعدهٔ پاراگراف ۴.۵)

| نوع رویداد فعالیت | token_primary | star/badge/item | score_war | score_settlement |
|---|---|---|---|---|
| MG_STAGE — موفقیت مرحلهٔ فردی | ✓ (فقط اولین موفقیت) | ✓ ستاره/نشان | △ اگر مرحله در پنجرهٔ هماورد باشد | ✗ |
| MG_PROD — اجرای مینی‌گیم تولید حرفه‌ای | **✗** (خروجی = خود محصول است؛ اجرای مجدد بدون مواد، محصول نمی‌دهد) | △ محصول با کیفیت حاصل اجرا | ✓ در پنجرهٔ هماورد | ✓ |
| SALE — فروش موفق در بازار | ✓ (به فروشنده، از کیف پول خریدار؛ خالص جدید نیست) | ✓ سابقه/اعتبار | △ تحویل سفارش هماورد | ✓ |
| PROJECT_CONTRIB — مشارکت در پروژه | **✗** (پاداش نقدی فقط در تحویل نهایی پروژه از بودجهٔ مصوب آن، یک‌بار) | ✓ نشان مشارکت | ✓ | ✓ |
| WAR_ACTION — اقدام امتیازآور هماورد | **✗** (پاداش نهایی فقط از خزانهٔ مصوب پس از نتیجه) | ✗ | ✓ | ✓ |
| MISSION_STEP — تکمیل گام مأموریت | ✓ (فقط اولین بار) | ✓ | △ | △ |
| PUZZLE_SOLVE — حل معما | ✓ (فقط اولین حل) | ✓ | △ | △ |
| DISCOVERY — کشف (منطقه/مخفی/سرنخ) | ✓ (فقط اولین کشف) | ✓ | △ | △ |
| EVENT_TASK — وظیفهٔ رویداد فصلی | △ فقط طبق قواعد مصوب همان رویداد | ✓ | △ | △ |

### ۴.۴ تضمین فنی

- هر grant یک رکورد `Reward` با کلید یکتای `(activity_event_id, grant_class)` دارد (سند ۱۴ §۶).
- پرداخت توکن همیشه از طریق `LedgerEntry` با `event_id` انجام می‌شود؛ شاخص یکتا روی `event_id + حساب + دسته` جلوی درج دوباره را می‌گیرد.
- محاسبهٔ پاداش **فقط سمت سرور** است؛ کلاینت فقط ورودی بازی را می‌فرستد (سند ۱۴ §۵).

### ۴.۵ قاعدهٔ بازپخش (Replay) [پیشنهادی]

- مرحلهٔ فردیِ قبلاً ستاره‌گرفته: بازپخش آزاد، اما `token_primary` فقط با ضریب کاهشی تکرار (نمونهٔ آزمایشی: تکرار ۱→۵۰٪، تکرار ۲→۲۵٪، تکرار ۳+→۰) [عدد آزمایشی].
- «چالش روزانه/هفتگی» یک رویداد فعالیت **جدید** با شناسهٔ جدید است (پس پاداشش دوبله محسوب نمی‌شود) با سقف روزانه [عدد آزمایشی].
- تولید مجدد محصول با مواد واقعی = رویداد جدید، اما شمارندهٔ ضدتولید-صوری سند ۱۱ §۴ آن را ارزیابی می‌کند.

## ۵. منابع ورود توکن (Faucets) و مصرف (Sinks)

### ۵.۱ ورود (فقط از سیستم)

| منبع | ترک | شرح | سقف |
|---|---|---|---|
| پاداش مرحله/مأموریت/معما/کشف فردی | INDIVIDUAL | طبق ماتریس §۴ | سقف روزانه [عدد آزمایشی] |
| پاداش دوره‌ای فعالیت (نسخهٔ روز/هفته) | INDIVIDUAL | هدفمند برای بازیکن تنهای فعال | سقف [عدد آزمایشی] |
| بودجهٔ مصوب پروژه‌ها | COLLECTIVE | در تحویل پروژه، یک‌بار، به مشارکت‌کنندگان طبق سهم مصوب | از خزانه/سیستم طبق بودجه |
| پاداش هماورد | COLLECTIVE | فقط از خزانهٔ مصوب سکونتگاه + تصحیح سیستم طبق قواعد اعلام‌شده | سقف [عدد آزمایشی] |
| رویدادهای فصلی | هر دو | طبق قواعد مصوب رویداد | سقف رویداد |

توجه: فروش در بازار **ورود جدید نیست** — انتقال از خریدار به فروشنده است؛ فقط کارمزد آن sink است.

### ۵.۲ مصرف (Sinks) — همه شفاف و دارای ارزش بازگشتی [قطعی: «هیچ Sink صرفاً برای گرفتن توکن طراحی نمی‌شود»]

| Sink | توضیح | سقف/نرخ |
|---|---|---|
| تعمیر و نگهداری ابزار | دوام ابزار به‌مرور کم می‌شود؛ تعمیر ارزان‌تر از خرید نو | نرخ [عدد آزمایشی] |
| هزینهٔ تولید | مواد مصرفی + هزینهٔ کارگاه/انرژی | طبق دستور (سند ۰۴) |
| کارمزد بازار | درصد کم و اعلام‌شده از فروش موفق | درصد [عدد آزمایشی — پیشنهاد ۲–۵٪] |
| هزینهٔ ثبت آگهی | ناچیز؛ جلوی آگهی‌بازی | [عدد آزمایشی] |
| ارتقای حرفه/مهارت/ابزار | پله‌های مهارت | طبقه‌بندی [عدد آزمایشی] |
| پروژه‌های عمرانی | بودجهٔ جمعی → کالای عمومی سکونتگاه | بودجه مصوب |
| خدمات سکونتگاه | انبار بزرگ‌تر، مسیر تجاری، … | قیمت مصوب |
| رویدادهای ویژه | ورود/آیتم رویداد | مصوب رویداد |

## ۶. وضعیت‌ها

- **رویداد فعالیت:** `OPEN → SETTLED (با پاداش‌ها) | VOID (ناموفق/لغو)` — SETTLED تغییرناپذیر.
- **پاداش (Reward):** `PENDING → GRANTED | REJECTED (با دلیل قابل اعتراض)`.
- **کیف پول:** موجودی همیشه ≥ ۰ (کنترل در تراکنش؛ سند ۱۴ §۴).

## ۷. ارتباط با سایر سیستم‌ها

| سیستم | رابطه |
|---|---|
| مسیر فردی (سند ۰۳) | تولیدکنندهٔ اصلی faucet INDIVIDUAL |
| حرفه‌ها (سند ۰۴) | sinkهای تولید/ارتقا؛ خروجی محصول به بازار |
| بازار محلی/عمومی (سند ۰۵–۰۷) | انتقال ارزش + کارمزد sink |
| پروژه‌ها (سند ۱۰) | sink بزرگ جمعی + faucet بودجه مصوب |
| هماورد (سند ۰۸) | فقط خزانه در ریسک است؛ پاداش نهایی یک‌بار |
| خزانه/رأی‌گیری (سند ۰۹) | تنها مسیر مجاز ریسک‌شدن دارایی جمعی |
| ضدتقلب (سند ۱۱) | ارزیاب همهٔ رویدادها |

## ۸. ریسک‌ها و کنترل

| ریسک | کنترل |
|---|---|
| تورم با faucet بی‌سقف | سقف روزانه/دوره‌ای + تنظیم با شبیه‌سازی سند ۱۵ |
| ماینینگ مکانیکی (تکرار بی‌پایان) | ضریب کاهشی بازپخش + شاخص تنوع سند ۱۱ §۴ |
| شست‌وشو بین حساب‌ها | ممنوعیت انتقال مستقیم + تحلیل گراف معاملات سند ۱۱ §۳ |
| double-spend | تراکنش اتمیک + رزرو (سند ۰۵ §۷، سند ۱۴ §۴) |
| پاداش دوبله | ماتریس §۴ + کلید یکتا |

## ۹. تست پذیرش (خلاصه — کامل در سند ۱۵)

1. یک `evt_*` دو بار claim شود → بار دوم رد می‌شود (idempotent).
2. مینی‌گیم تولیدی بدون مصرف مواد → هیچ محصول/پاداشی نمی‌دهد.
3. فروش + مشارکت پروژه + هماورد برای همان کالا → فقط فروش token_primary می‌دهد؛ بقیه امتیازی‌اند.
4. موجودی منفی در هیچ مسیری ممکن نیست.
5. سقف روزانه در هر ۴ مسیر مستقل کنترل می‌شود.

## ۱۰. نیازمند تصویب کارفرما

1. نام توکن (§۲).
2. ممنوعیت انتقال مستقیم توکن بین بازیکنان (§۲).
3. ماتریس پاداش §۴.۳ به‌عنوان مرجع نهایی.
4. ضریب کاهشی بازپخش و سقف‌های روزانه — پس از شبیه‌سازی (سند ۱۵).
5. بازهٔ کارمزد بازار.

**وضعیت این سند: ✅ طراحی کامل (اعداد آزمایشی) — آمادهٔ شبیه‌سازی و تصویب.**
